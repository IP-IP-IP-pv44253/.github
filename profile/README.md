<h2>数量算错，多半是把「账号」当成了「单元」</h2>
<p>问「需要几个 IP」，得到的常见答案是「一个店铺一个」。这句话听起来清楚，实际用起来经常出问题，因为它没区分「店铺」和「经营主体」。同一主体开五个店，和一个主体开一个店，需要的出口数量完全不同。</p>
<p>正确的算法从一个更基础的单位出发：隔离单元。一个需要独立网络身份的运营主体，才算一个单元。</p>

<p>三步里，第二步是省钱的关键，第三步是保命的关键。两个都做对，数量既不会浪费也不会不够。</p>

<h2>什么算一个单元</h2>
<p>三个判断标准。一，注册信息是否独立：独立的营业执照、独立的法人主体，算一个单元。二，资金是否独立：独立的收款账户，算一个单元。三，经营地是否独立：不同国家或不同发货地，算一个单元。</p>
<p>三项里任意一项独立，就应该单独一条出口。三项全部共享的多个店铺，可以合并为一个单元。</p>

<h3>为什么资金独立是硬边界</h3>
<p>因为资金链路是平台判定关联时权重很高的信号。出口相同且资金不同，或者出口不同但资金相同，都可能被连起来看。所以资金独立的两个主体，出口必须分开。</p>
<h3>多市场运营怎么算</h3>
<p>一个主体做美国站和欧洲站，算两个单元还一个？取决于平台是否把不同站点视为独立。多数情况下，同一主体在不同站点可以用同一出口，但若两侧的注册信息不同，就需要分开。拿不准时按分开算，成本增加有限，风险降低明显。</p>

<h2>备用数量怎么定</h2>
<p>建议按单元数的两成左右预留，至少留一条。备用的作用不是「多开一个店」，而是「出问题时能立刻替换」。</p>
<p>没有备用的后果很具体：某条出口被封或故障，需要临时采购，等待期可能几天到几周。这几天里对应的店铺无法正常运营，损失通常超过备用地址几个月的费用。</p>

<h2>数量的上限受什么约束</h2>
<p>三个约束。一，预算。每条出口都是固定成本。二，管理能力。十条以内可手工管理，再多就需要台账与监控。三，设备与环境。出口多了，配套的设备或浏览器环境也要跟上，这部分成本常被低估。</p>
<p>第三个约束最容易失衡。买了十条出口却只有三套环境，实际只能用三条，其余闲置。</p>

<h2>数量算多了会怎样</h2>
<p>不只是浪费钱。闲置地址会带来两个隐性成本：一是管理负担，需要维护与巡检；二是决策惰性，因为「还有空着的」，容易在不该扩张的时候扩张。</p>
<p>更实际的做法是按当前活跃单元下单，业务增长时按批追加。追加单价可能略高，但总成本更低。</p>

<h2>一份可直接套用的清单</h2>
<p>一，列出所有店铺。二，按主体、资金、经营地三项归并，得到单元数。三，为每个单元分配一条出口。四，加两成备用。五，检查设备或环境数量是否匹配。六，建立台账。</p>
<p>六步走完，数量问题就解决了。之后每季度复核一次，因为主体和店铺会变。</p>

<h2>常见问答</h2>
<h3>十个店需要十个 IP 吗</h3>
<p>不一定。若十个店属于同一主体、共用资金，可以合并。若分属不同主体，就需要分开。</p>
<h3>一条 IP 能带几个店</h3>
<p>同一主体下没有硬限制，取决于并发与带宽。运营角度建议不超过业务实际需要，避免出口行为过于集中。</p>
<h3>备用要一直付费吗</h3>
<p>多数方案按条计费，备用也是成本。可以选较便宜的档位做备用，只要能应急替换即可。</p>
<h3>算少了怎么办</h3>
<p>追加。但追加需要时间，且新地址需要适应期。这就是为什么要留备用，而不是算得刚好。</p>
